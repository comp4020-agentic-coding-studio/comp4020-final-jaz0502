# Rules for working on the community garden

These come from `README.md`, which says what "good" means for this app. If a rule here and the README disagree, fix both in the same step.

## What this app must never do

- Never add scoring, points, rankings or any win or lose state. The garden is a shared, collaborative space.
- Decorations for your own garden, and then a pet, are the rewards, and they stay private. Never compare them between gardeners, rank them, show them to anyone else, put a clock on them, or take one back.
- Never send a visitor's `gid` cookie to anyone. It is their whole identity. Clients only get the one-way `publicId(gid)`, and anything leaving the server goes through `toPublic()` in `src/routes.ts`. `spec/privacy.test.ts` enforces this.
- Never let one visitor overwrite or remove another's healthy plant. Planting only works on an empty plot, and composting only on a wilted one.
- Never put a gardener's figure on the plots. Figures walk only along the flagstone paths: the ring round each bed and the walkways between neighbouring beds.
- Never turn a gardener's record of what they have planted, watered and composted into a score. It stays a plain record, private to them: never shown to anyone else, never compared between gardeners, and never given levels, streaks, badges, achievements or targets of its own. Its one use is that waterings unlock decorations (see below). Word it as a record ("Planted 12"), never as an achievement.

## What a change must not break

- Anyone can plant an empty plot and water any plot. Nobody owns a plot in the shared garden. `spec/plots.test.ts` enforces this.
- Watering resets the wilt clock, and a wilted plot cannot be watered or replanted until someone composts it.
- A plot's stage is derived from stored timestamps by `derivePlot` in `src/garden.ts`. Never use a per-plot timer, because Fly stops the machine when it is idle. The database only stores `empty` or `planted`.
- Live updates go over Server-Sent Events (`/events`). The page changes in response to those events, not to the POST response.
- A figure's position is only for show. Where a gardener's figure stands, or which bed they are looking at, never limits what anyone can do to a plot, and no action may depend on it.
- The garden has four beds of 25 plots, numbered by bed: 0 to 24, 25 to 49, 50 to 74 and 75 to 99. A bed's plots keep their numbers, so a new bed is added after the last one and never renumbers the others. `spec/plots.test.ts` and `spec/migration.test.ts` enforce this.
- Each bed has a name and a theme, and takes only the plants that fit it: The Cottage Garden takes lavender, rosemary and foxglove, The Flower Garden tulips, sunflowers and flower shrubs, The Fruit Garden apple trees, strawberries and blueberries, and The Vegetable Garden carrots, tomatoes and lettuces. `BEDS` in `src/garden.ts` is the one place that says so. The server turns away a plant the bed does not take (409, logged with `reason=wrong-bed`, and it counts against the person's limit), and the page reads the list from `hello` and only follows it, so a request sent by hand gets the same answer as a click. Only planting is restricted: anyone may still water or compost in any bed. A plant already in a bed before it had a theme stays until it wilts. Stored plant types never change when a plant is renamed, so a tulip is still `flower`, an apple tree `tree` and a carrot `vegetable`. `spec/beds.test.ts` enforces this.
- The camera is a way of looking and nothing more. Photo mode hides the panels and draws a frame over the page's own view. It sends nothing to the server, has no endpoint and no log line, and while it is open nothing in the garden can be clicked, so it never limits or depends on what anyone can do. A photo is kept only in the gardener's own browser (IndexedDB, at most 24, never uploaded) and nobody else can see it. Never share photos or show a photo count or total, and never give photos goals, streaks, badges, or "first" or "most photographed" wording. Call it "Album", never an achievement. When the album is full or storage is blocked, say so and offer Save to device. Never drop a kept photo silently. No spec can check this, because the server is not involved, so it is judged in a real browser and listed as judged in the README.
- Gathering seeds only reads a fully grown plant and never changes it, so nobody's plant is harmed. The server checks that the plant is mature, and gives each gardener seeds from one plant once in its life, at most 6 of a kind. A gardener's seeds are kept by public id, never the cookie, and sent only to their own streams as a `seeds` event. They are never broadcast or put in Recent, and each gather is logged and counts against the action limit. Seeds are what you can plant, not a collection: never show a total, a number of kinds, goals, badges or "new" markers. `spec/seeds.test.ts` enforces this.
- Caring for the garden unlocks decorations for your own garden: a bench, a picket fence, a lantern, a scarecrow, a rustic fence, a gnome, a birdbath and a stone wall, in one fixed list in `src/decorations.ts`. Each one has one task, the same for everyone and in the same order (`TASKS`: water plants, feed cows, pat hens, plant seeds, gather seeds, compost), so nobody chooses an order to chase. Only the task you are on counts, and finishing it unlocks the next decoration and starts the next task. A watering counts only in the shared garden and only on a plot nobody has watered in the last 10 minutes; a cow or hen counts again for the same gardener only after `ANIMAL_GAP_MS`, so one animal can't be fed or patted over and over; and anything in your own garden never counts. Feeding a cow and patting a hen are drawn only in each visitor's page, which tells the server with `POST /api/animals/{cow|hen}/{n}` only so it can be counted: it is validated (404, `reason=no-such-animal`), counts against the action limit, is logged (`did=feed-cow` or `did=pat-hen`, with `reason=too-soon` when it did not count), changes nothing in the garden and is never broadcast or put in Recent. The server decides what you have unlocked, and a request for a locked decoration gets 409, logged with `reason=locked`. Unlocked decorations are kept by public id, never the cookie, sent only to your own streams as a `decorations` event, never broadcast or put in Recent, and never taken back, even when plants wilt. The journal may say the one task you are on and how many more of it are left ("Next decoration: feed 3 more cows"), and nothing more: no totals, no "x of y", no list of the tasks still to come, no timers, daily goals, streaks, rarity, or wording about winning. Placing a decoration only changes how your own garden looks and never limits or depends on anything in either garden. A watering that did not count says so, so your record and your next decoration do not look like they disagree: the reply to your own watering carries `credit` (`counted`, `rested` when the plot was watered a moment ago, or `other-task` when watering is not what you are on), and the page shows one short note for `rested`, and once for `other-task`. It is told to the one who watered and nobody else, never broadcast, never put in Recent, and never a total, a timer or a number of minutes. Each unlock and each refusal is logged. `spec/decorations.test.ts` and `spec/tasks.test.ts` enforce this.
- A pet is the next reward after the last decoration, so it needs no new credit: `petUnlocked(credit)` in `src/pets.ts` is true once all eight decorations have unlocked, and the server decides. It is for your own garden only: one pet per gardener, a kind from `PET_KINDS` (cat, dog, rabbit, sent in `hello`) and a name. The name is the one piece of text a visitor types, so it is 1 to 12 letters (no digits, spaces or marks), made to start with a capital by the server, and checked there (400, `reason=bad-name`), and it is never logged, never put in Recent, never broadcast and never shown to anyone else. A pet is kept by public id, never the cookie, sent only to its owner's streams as a `pet` event, and never taken back. Adopting, renaming or changing kind goes through `POST /api/own-garden/pet`, counts against the action limit, and logs `did=pet` with the kind, or `reason=locked` (409), `bad-kind`, `bad-name` or `too-many-gardeners`. Stroking and feeding a pet, like petting a hen, are drawn only in your own page: nothing is sent, stored, counted or logged, there is no hunger, level or streak, and where the pet is never limits or depends on anything. `spec/pet.test.ts` enforces this.
- The barn and the cottage can be walked into. Inside is a private view, like the camera and your own garden: clicking the building (or its sign) fades you into a room far from the garden, where you walk about with the camera behind your own figure (W A S D, arrow keys, drag to turn, a stick on a touch screen) and cannot leave the room. Nothing is sent to the server, so there is no endpoint and no log line; your own figure is drawn inside, only in your own page and never sent, and nobody else's is, so the rule that figures walk only on flagstones is about the shared garden. Going in or out never depends on where your figure stands and nothing in either garden depends on whether you are inside. Photo mode still works inside. In the barn you can give the cows hay, which counts towards a decoration through `tellAnimal` the same as outside. In the cottage your pet is with you and can be stroked or fed, and nobody else sees it. No spec can check this, because the server is not involved, so it is judged in a real browser and listed as judged in the README when the README is next updated.
- The fences and arches round the beds are only for show. They never limit where a figure walks or what anyone can do.
- The server never knows the paths' shape. A figure is sent as `u` and `target` from 0 up to 1, and the page reads each quarter as one bed's loop. Walking between beds is worked out in the page.
- Presence lives in memory only and is keyed by the public id, so two tabs from one browser are one gardener with one figure. A stranger's browser is a source of messages, so `POST /api/presence` stays validated, rate-limited and capped (`src/presence.ts`). `spec/presence.test.ts` enforces this.
- Plant, water and compost are limited per gardener: a budget of actions in a window of time (15 in 10 seconds by default, `ACTION_LIMIT` and `ACTION_WINDOW_MS`), checked on the server by public id before anything else is done. Every attempt counts, refused ones too. Past it the server answers 429 with `Retry-After` and changes nothing, and logs it once for the window so a flood cannot flood the log. The page holds off when told to, but only the server's limit counts. `spec/limits.test.ts` enforces this.
- A wave is a hello and nothing more. It is never stored, counted, ranked or sent to anyone in particular, and `POST /api/wave` stays validated, rate-limited, and open only to someone with the event stream open (`src/presence.ts`). `spec/wave.test.ts` enforces this.
- A gardener's record lives in `gardener_stats`, keyed by the public id and never the cookie, and is sent only to that gardener's own streams as a `stats` event, never broadcast. Only a capped number of gardeners are counted. `spec/stats.test.ts` enforces this.
- The "Recent" panel is a glance at what has just happened, not a history or a tally: the last few plants, waterings and compostings, newest first, capped in `src/activity.ts` and kept in memory only. It shows no counts or totals, no "most" or "top" wording, and no way to filter by gardener or look further back, so it can't become a leaderboard. Entries carry the public id and never the cookie, and refused actions and waves are left out. A new action that changes the garden goes in it. `spec/feed.test.ts` enforces this.
- The server says what each gardener does, one `key=value` line to stdout for each plant, water, compost and wave (and for each one refused, with a reason), and for each gardener joining or leaving, so `flyctl logs` shows who did what. Every line goes through `logEvent` in `src/log.ts`, which takes the public id and never the cookie. Figure moves are not logged, because they are many and say nothing. A new action gets a log line and a spec. `spec/logging.test.ts` enforces this.
- The course invariants keep passing: `/` returns 200 and `/readme/` publishes the README's headings.
- The app runs on one 256 MB Fly machine with one volume at `/data`. Do not change the fixed settings in `fly.toml`.

## How to work

- Work one step at a time. Show the result and wait for approval before the next step. Do not commit or push unless asked, and commit each step separately.
- Check anything visual in a real browser, not just with types and tests.
- Before a deploy, build the Docker image and run `pnpm check` against it, as CI does. CI deploys every push to `main`, so only deploy by hand if asked.
- When a rule changes, change the spec and the README in the same step. A claim in the README must match what a spec enforces or be listed as judged.
- Never move the `crit-8` tag again. It is frozen on `0d788b8`, because after a crit's cutoff its tag records what the tutor marked. Later crits get their own tags (`crit-9`, `crit-10`), made only when asked.
- In the process docs, say who did what. If the agent ran a check or a restart, say so, and do not invent sources or claim the author read or did something they did not.
